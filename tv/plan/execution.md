# תוכנית ביצוע — למודל / לסוכנים שיפתחו את הפרויקט

[← חזרה לתוכנית](../plan.md)

המסמך הזה מיועד **למודל שיבצע את הפיתוח**. הוא קובע:
באיזה סדר מפתחים, איך מחלקים בין סוכנים (agents), מי אחראי על אילו קבצים, איך מעבירים עבודה ביניהם, ומתי משהו נחשב "גמור".
את הפירוט של כל משימה יש לקרוא בקובץ המשימה עצמו (S1, A3 וכו' — קישורים ב-[plan.md](../plan.md)).

---

## 1. ההמלצה: כן לפצל — אבל ל-4 סוכנים בלבד

| סוכן | אחריות | משימות |
|---|---|---|
| **Lead** (מוביל / ארכיטקט) | חוזה ה-API, שלד הפרויקט, שרת דמה, מיזוגים, החלטות | S5, שלב 0, נקודות אינטגרציה |
| **Server** | כל קוד השרת | S1, S4, S2, S3, חלק השרת של P3 |
| **App** | כל קוד האפליקציה | A1, A2, A3, A6, A4, A5, חלק האפליקציה של P3 |
| **Ops** | Windows, בנייה, מדריכים, בדיקות מקצה לקצה | P1, P2, R1, R2, סקריפט ההמרה ומדריך P3 |

### למה דווקא כך
- **השרת והאפליקציה עצמאיים לגמרי** — מדברים רק דרך ה-API. ברגע שהחוזה (S5) קפוא, אפשר לפתח אותם במקביל בלי התנגשויות.
- **לא לפצל את השרת לכמה סוכנים:** S1/S2/S4 נוגעים באותם קבצים (סריקה, `library.json`, state) — פיצול יגרום להתנגשויות ולכפילויות.
- **לא לפצל את האפליקציה בהתחלה:** A1 קובע עיצוב, ניווט ומבנה — כל השאר תלוי בו. **אחרי** ש-A1+A3 גמורים אפשר (לא חובה) להוסיף סוכן App-2 לנגן (A6) בזמן ש-App ממשיך ל-A4/A5, כי הם בקבצים נפרדים (`player/` לעומת `ui/`).
- **Ops נפרד** כי העבודה שלו (סקריפטים של Windows, CI, תיעוד, בדיקות) לא נוגעת בקוד, ומשחררת את שני הסוכנים הכבדים.
- יותר מ-4–5 סוכנים = יותר זמן על תיאום ומיזוגים מאשר על פיתוח.

### אם יש רק סוכן אחד
עובדים באותו סדר בדיוק (שלב 0 ← 1 ← 2 ← 3), ובתוך כל שלב: שרת ← Ops ← אפליקציה. מדלגים על שרת הדמה (משתמשים בשרת האמיתי).

## 2. סדר העבודה — גלים (waves)

```
שלב 0 (Lead, לבד)         חוזה API קפוא + שלד + שרת דמה
        │
        ▼
שלב 1 (במקביל)      Server: S1 + S4 + API סרטים
                    App:    A1 + A2 + A3 (מול שרת הדמה)
                    Ops:    CI ל-APK + start-server.bat + P1
        │
        ▼  ★ אינטגרציה 1 (Lead + Ops): האפליקציה מול השרת האמיתי, צפייה בסרט
        │
שלב 2 (במקביל)      Server: S2 + S3 + P3-שרת (ffprobe, speedtest)
                    App:    A6 (נגן) ← A4 ← A5
                    Ops:    P2 (אשף, הפעלה אוטומטית, חומת אש) + סקריפט המרה
        │
        ▼  ★ אינטגרציה 2: סדרות, פרק הבא, חיפוש, TMDB
        │
שלב 3 (במקביל)      App:    P3-אפליקציה (מסך מידע, בדיקת מהירות, באפר, tunneling)
                    Server: תיקוני באגים, ביצועים (2,000+ קבצים)
                    Ops:    R2 בדיקה מלאה, מדריך משתמש, R1 Release
        │
        ▼  ★ גרסה 1.0
```

### שלב 0 — Lead (חייב להסתיים לפני כל השאר)
1. להפוך את [S5](server/05-api.md) ל**חוזה קפוא**:
   - `tv/contract/api.md` — כל נקודת קצה, פרמטרים, קודי שגיאה.
   - `tv/contract/fixtures/*.json` — תשובה לדוגמה לכל נקודת קצה (סרטים, סדרה עם 2 עונות, home, search, play, profiles).
2. **שרת דמה** `tv/contract/mock-server.js`: מגיש את ה-fixtures + 2 קבצי וידאו קצרים לבדיקה (נוצרים עם ffmpeg). כך האפליקציה מתפתחת בלי לחכות לשרת.
3. **שלד תיקיות** (ראו סעיף 3) ו-`tv/CONVENTIONS.md`.
4. **החלטה על טיוטת הקוד הקיימת** (`tv/server`, `tv/android`): לא להשתמש בה כמו שהיא. מותר להעתיק ממנה חלקים שכבר נבדקו (ראו סעיף 6), אבל המבנה נקבע לפי התוכנית.
5. `tv/STATUS.md` — לוח מצב משותף (ראו סעיף 4).

**סיום שלב 0:** שרת הדמה רץ, כל ה-fixtures תואמים לחוזה, ושלושת הסוכנים קיבלו את ההנחיות.

### נקודות אינטגרציה (★)
- Lead ממזג את הענפים, Ops מריץ את תרחישי הבדיקה הרלוונטיים מ-[R2](delivery/02-testing.md).
- כל באג נרשם ב-`STATUS.md` עם הסוכן האחראי.
- **לא מתחילים את השלב הבא** לפני שהאינטגרציה עוברת.

## 5. שינוי בחוזה ה-API
1. הסוכן כותב בקשה ב-STATUS (מה, למה, דוגמה).
2. Lead מעדכן את `contract/api.md` + fixtures + שרת הדמה, ומגדיל גרסה (`apiVersion`).
3. Server ממש, App מתאים.
**לעולם לא:** שהאפליקציה תסתמך על שדה שלא מופיע בחוזה, או שהשרת ישנה צורה של תשובה בלי עדכון החוזה.
**שינויים מותרים בלי תיאום:** הוספת שדה אופציונלי חדש לתשובה (האפליקציה מתעלמת משדות לא מוכרים).

## 6. הנחיות לכל סוכן

### Server
- Node.js LTS (20+), **בלי תלויות חיצוניות** אם אפשר (ffmpeg/ffprobe — אופציונלי, מזוהה בזמן ריצה). אם חייבים תלות — לנמק ב-STATUS.
- מבנה: `tv/server/src/*` כמו ב-[S1](server/01-core.md#מבנה-קבצים-מתוכנן).
- בדיקות: `node --test` (מובנה ב-Node). חובה לכל לוגיקה: ניקוי שמות, זיהוי פרקים, Range, קידוד כתוביות, כללי "נצפה".
- TMDB בבדיקות — תשובות מוקלטות בלבד, בלי רשת.
- **מותר להעתיק מהטיוטה** `tv/server/server.js` (נבדקה ידנית ועבדה): Range streaming, המרת Windows-1255, גילוי UDP, ניקוי שמות.
- סדר פנימי: S1 ← S4 ← נקודות קצה של סרטים ← (אינטגרציה 1) ← S2 ← S3 ← P3-שרת.

### App
- Kotlin, Compose for TV (`androidx.tv:tv-material`), Media3, Coil. minSdk 23.
- **פיתוח מול שרת הדמה** עד אינטגרציה 1.
- **חשוב — סביבת בנייה:** אם הסביבה לא יכולה להוריד את Android SDK (כמו בסביבת הענן שבה נכתבה הטיוטה — dl.google.com חסום), הבנייה נעשית **רק דרך GitHub Actions**. אחרי כל push: לבדוק את ריצת ה-workflow ולתקן שגיאות קומפילציה לפני שממשיכים. **אין לסמן משימה כגמורה בלי בנייה ירוקה.**
- טיוטת האפליקציה הקיימת **מעולם לא קומפלה** — להתייחס אליה כרעיון בלבד (מותר להעתיק את `PlayerActivity` ו-`ServerApi` כנקודת התחלה, ולוודא שהם עוברים בנייה).
- בדיקות: יחידה ל-ViewModels (עם Repository מדומה); בדיקת UI אחת לניווט בחיצים.
- סדר פנימי: A1 ← A2 ← A3 ← (אינטגרציה 1) ← A6 ← A4 ← A5 ← P3-אפליקציה.
- כל טקסט בממשק בעברית, ב-`strings.xml` (לא בקוד).

### Ops
- כל הסקריפטים ל-Windows (`.bat` / PowerShell) — מקודדים UTF-8, עם `chcp 65001` לעברית.
- CI: workflow שבונה APK וגם מריץ את בדיקות השרת; Release עם APK + ZIP של השרת.
- מדריכים למשתמש בעברית ב-`tv/docs/`, מבוססים על P1/P2/P3.
- בכל אינטגרציה: מריץ תרחישים מ-R2 ומדווח ב-STATUS.
- סדר פנימי: CI + start-server.bat + P1 ← (אינטגרציה 1) ← P2 + סקריפט המרה ← R2 + R1.

## 8. הנחיות פתיחה מוכנות (להדביק לכל סוכן)

**Lead:**
> אתה הסוכן המוביל של פרויקט "הסרטים שלי" בתיקייה `tv/`. קרא את `tv/plan.md`, את `tv/plan/execution.md` ואת כל קבצי `tv/plan/**`. בצע את שלב 0 בדיוק כמתואר בסעיף 2: חוזה API קפוא ב-`tv/contract/`, fixtures, שרת דמה, `CONVENTIONS.md`, `STATUS.md`. אחר כך נהל את נקודות האינטגרציה ובקשות לשינוי חוזה. אל תכתוב קוד שרת או אפליקציה בעצמך.

**Server:**
> אתה סוכן השרת של פרויקט "הסרטים שלי". קרא את `tv/plan.md`, `tv/plan/execution.md`, `tv/contract/api.md` ואת `tv/plan/server/*`. אתה עובד רק בתוך `tv/server/` ובענף `tv-server`. בצע לפי הסדר: S1, S4, נקודות הקצה של סרטים, ואחרי אינטגרציה 1 — S2, S3 וחלק השרת של P3. עמוד בחוזה בדיוק; בקשות לשינוי — דרך `tv/STATUS.md`. עדכן את STATUS בסוף כל משימה.

**App:**
> אתה סוכן האפליקציה של פרויקט "הסרטים שלי" (Android TV). קרא את `tv/plan.md`, `tv/plan/execution.md`, `tv/contract/api.md` ואת `tv/plan/app/*` ו-`tv/plan/pc/03-smooth-playback.md`. אתה עובד רק בתוך `tv/android/` ובענף `tv-app`. פתח מול שרת הדמה (`tv/contract/mock-server.js`). סדר: A1, A2, A3, ואחרי אינטגרציה 1 — A6, A4, A5, ואז חלק האפליקציה של P3. ודא בנייה ירוקה ב-GitHub Actions אחרי כל push. עדכן את `tv/STATUS.md`.

**Ops:**
> אתה סוכן ה-Ops של פרויקט "הסרטים שלי". קרא את `tv/plan.md`, `tv/plan/execution.md`, `tv/plan/pc/*` ו-`tv/plan/delivery/*`. אתה אחראי על `tv/scripts/`, `tv/docs/` ועל ה-workflows. סדר: CI שבונה APK ומריץ בדיקות שרת, `start-server.bat`, מדריך P1; אחרי אינטגרציה 1 — P2 וסקריפט ההמרה; בסוף — R2 ו-R1. בכל נקודת אינטגרציה הרץ את תרחישי R2 הרלוונטיים ודווח ב-`tv/STATUS.md`.

## 9. הערכת היקף (גסה)
| שלב | עומס יחסי |
|---|---|
| 0 | קטן |
| 1 | בינוני–גדול (בעיקר App) |
| 2 | גדול (S3 + A6 הם הכבדים ביותר) |

**נתיב קריטי:** שלב 0 ← A1 ← A3 ← A6 ← A4. הסוכן App הוא צוואר הבקבוק — לכן אם מוסיפים סוכן חמישי, הוא App-2 לנגן (A6) מתחילת שלב 2.
